# Upgrading to v0.24

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.24.0"}
  ]
end
```

## Filters are configured like fields

The built-in filters `Backpex.Filters.Boolean`, `Backpex.Filters.MultiSelect`, `Backpex.Filters.Range` and
`Backpex.Filters.Select` are generic: you configure them in your LiveResource and no longer need a module for each
filter.

```elixir
# Before
defmodule MyAppWeb.Filters.PostLikeRange do
  use Backpex.Filters.Range

  @impl Backpex.Filters.Range
  def type, do: :number

  @impl Backpex.Filter
  def label, do: "Likes"
end

likes: %{module: MyAppWeb.Filters.PostLikeRange}

# After
likes: %{module: Backpex.Filters.Range, label: "Likes", type: :number}
```

The options of each filter module are described in its documentation, the options every filter takes in
`Backpex.Filter`. Modules that `use` a built-in filter still work: their callbacks, such as `options/1` and `prompt/0`,
are the defaults of the options. New options for every filter:

- `:can?` hides a filter unless the function returns `true` for the assigns, in addition to `c:Backpex.Filter.can?/1`.
- `:condition` replaces `c:Backpex.Filter.condition/3` of the filter module.

Backpex now validates the options of filters, as it does for fields, and raises for an unknown or invalid option. A
filter needs a `:label` option unless its module implements `c:Backpex.Filter.label/0`. If you put keys into your filter
maps that Backpex doesn't know, remove them, or define them with the `:config_schema` option of `use Backpex.Filter`.

### The callbacks of filters receive the filter

The callbacks of `Backpex.Filter` receive the filter as a `{name, config}` tuple, where `config` is the validated map of
its options. Update your custom filters and the callbacks you override in modules that use a built-in filter:

- `type/1` is now `c:Backpex.Filter.type/2`. A filter that still defines `type/1` doesn't compile.
- `validate/2` is now `c:Backpex.Filter.validate/3`. Its first argument is the filter. A filter that still defines
  `validate/2` doesn't compile.
- The second argument of `c:Backpex.Filter.changeset/3` is the filter instead of the field. A `changeset/3` that still
  passes its second argument to an `Ecto.Changeset` validation compiles, but raises a `FunctionClauseError` in
  `Ecto.Changeset.validate_change/3` when the index view is opened.
- The first argument of `c:Backpex.Filter.condition/3` is the filter instead of the field.
- `c:Backpex.Filter.render/1` and `c:Backpex.Filter.render_form/1` find the filter in `@filter`. The render functions of
  the built-in filters read their options from it, they no longer take `@options`, `@prompt` or `@type`.

```elixir
# Before
@impl Backpex.Filter
def type(_assigns), do: :integer

@impl Backpex.Filter
def changeset(changeset, field, _assigns), do: validate_number(changeset, field, greater_than: 0)

@impl Backpex.Filter
def condition(field, value, _assigns), do: expr(ref(^field) >= ^value)

# After
@impl Backpex.Filter
def type(_filter, _assigns), do: :integer

@impl Backpex.Filter
def changeset(changeset, {field, _config}, _assigns), do: validate_number(changeset, field, greater_than: 0)

@impl Backpex.Filter
def condition({field, _config}, value, _assigns), do: expr(ref(^field) >= ^value)
```

Code that calls the callbacks of filters directly, e.g. a custom adapter, passes the filter as well. The filters in the
`:filters` assign are validated. `Backpex.LiveResource.active_filters/1` returns validated filters, too.

## Data access goes through the adapter

Backpex is Ecto-first, but outside of `Backpex.Adapters.Ecto` it no longer builds queries, calls the repo or inspects
schemas. The views, fields, filters and metrics read and write data through `Backpex.Adapter` callbacks, mostly via
`Backpex.Resource`. Filters return expressions and metrics name an aggregate, which the adapter turns into queries.
Options and callbacks that take Ecto queries moved to the Ecto adapter.

If you use the Ecto adapter and the built-in fields, check the sections on filters, metrics, `Backpex.Fields.BelongsTo`,
search and deleting items.

### Filters return expressions

Filters no longer build queries. The `query/4` callback of `Backpex.Filter` is replaced by
`c:Backpex.Filter.condition/3`. It returns an expression, written with `Backpex.Expr.expr/1`, such as
`expr(status == "open")`, which the adapter turns into a query. `use Backpex.Filter` imports `expr/1`. See
`Backpex.Expr` for all operators and functions, paths through relationships and `exists/2`. The built-in filters already
return expressions. If your filter uses a built-in filter and overrides its `query/4`, override `condition/3` instead. A
filter that still defines `query/4` doesn't compile.

`use Backpex.Filters.Boolean` and the other built-in filters no longer import `Ecto.Query`, and neither does
`use BackpexWeb, :filter`. Add `import Ecto.Query` to your filters that use it, e.g. to load their options. Without it,
a `dynamic([post], ...)` expression doesn't compile, e.g. with `undefined variable "post"`.

Backpex checks the fields of the expressions of filters and metrics and casts their values to the types of the fields.
An expression with an unknown field, or with a path through a relationship to many items, raises an `ArgumentError`
when the index view applies it.

The predicates of a `Backpex.Filters.Boolean` filter are expressions:

```elixir
# Before
%{label: "Published", key: "published", predicate: dynamic([x], x.published)}

# After
%{label: "Published", key: "published", predicate: expr(published == true)}
```

Replace the `query/4` callback of your custom filters with `condition/3`. Inside `expr/1`, a name refers to a field of
the items, `ref(^field)` to the field the filter is configured for, and `^` takes the value of an Elixir expression:

```elixir
# Before
@impl Backpex.Filter
def query(query, attribute, value, _assigns) do
  where(query, [x], field(x, ^attribute) >= ^value)
end

# After
@impl Backpex.Filter
def condition({field, _config}, value, _assigns), do: expr(ref(^field) >= ^value)
```

The first argument of `condition/3` is the filter, see [Filters are configured like fields](#filters-are-configured-like-fields).

A filter can't join tables or select distinct items anymore, as the adapter decides how to join, order and paginate the
items. Replace a join with `exists/2`, which keeps the items with at least one matching related item:

```elixir
# Before
@impl Backpex.Filter
def query(query, _attribute, tag_ids, _assigns) do
  query
  |> join(:left, [post], t in assoc(post, :tags), as: :tag)
  |> where([tag: t], t.id in ^tag_ids)
  |> distinct([post], post.id)
end

# After
@impl Backpex.Filter
def condition(_filter, tag_ids, _assigns), do: expr(exists(tags, id in ^tag_ids))
```

With the Ecto adapter, the `distinct` of such a join also sorted the items by their primary key first, so the order the
user selected didn't apply while the filter was active. `exists/2` keeps the order.

If a filter needs an expression that only the Ecto adapter understands, e.g. a fragment of SQL, wrap an
`Ecto.Query.dynamic/2` expression with `Backpex.Expr.native/2`. Such a filter only works with the Ecto adapter:

```elixir
@impl Backpex.Filter
def condition({field, _config}, value, _assigns) do
  Backpex.Expr.native(Backpex.Adapters.Ecto, dynamic([event], fragment("lower(?)", field(event, ^field)) == ^value))
end
```

Tests that call `query/4` of a filter can call `condition/3` and compare the expression, or read the items that match
it with a `Backpex.Query`:

```elixir
filter = {:status, %{module: MyAppWeb.Filters.Status}}

{:ok, posts} =
  MyAppWeb.PostLive
  |> Backpex.Query.new()
  |> Backpex.Query.filter(Backpex.Filter.to_condition(filter, "draft", %{}))
  |> Backpex.Resource.read()
```

The Ecto adapter names the binding of the schema like `Backpex.Adapters.Ecto.name_by_schema/1`, e.g. `:post`, so a
native expression of the filter can use it, as in `dynamic([post: p], ...)`.

### Metrics name an aggregate

`Backpex.Metrics.Value` takes an `:aggregate`, such as `{:sum, :likes}`, and an optional `:where` expression, such as
`[published: true]` or `expr(likes > 10)`. Its
`:select` expression still works with the Ecto adapter, but an aggregate works with every adapter:

```elixir
# Before
total_likes: %{module: Backpex.Metrics.Value, label: "Total likes", select: dynamic([p], sum(p.likes))}

# After
total_likes: %{module: Backpex.Metrics.Value, label: "Total likes", aggregate: {:sum, :likes}}
```

See `Backpex.Metric` for all aggregates. `use BackpexWeb, :metric` no longer imports `Ecto.Query`.

The `query/3` callback of `Backpex.Metric` is gone. A metric module that gets its data in another way implements
`c:Backpex.Metric.data/3` instead. Backpex calls it instead of the adapter, with the metric, the `Backpex.Query` of the
items of the index view (after the search and the active filters, on all pages) and its assigns. A metric module with `use BackpexWeb, :metric` that still defines
`query/3` without `data/3` doesn't compile. For other metric modules, Backpex raises when it computes the metric.

`query/3` received an Ecto query that the `item_query`, the search and the filters already limited. `data/3` receives
a `Backpex.Query` instead. To compute the data from the items of the index view, read it with
`Backpex.Resource.read/1`. Backpex applies the `scope/1`, the search and the filters, as it did for `query/3`:

```elixir
# Before
@impl Backpex.Metric
def query(query, _select, repo) do
  query |> repo.all() |> Enum.map(&MyApp.Orders.total/1) |> Enum.sum()
end

# After
@impl Backpex.Metric
def data(_metric, query, _assigns) do
  {:ok, orders} = Backpex.Resource.read(query)

  orders |> Enum.map(&MyApp.Orders.total/1) |> Enum.sum()
end
```

A metric that reads its data elsewhere, e.g. from a function of your context module, has to limit the data itself, e.g.
to the items the current user may see:

```elixir
# Before
@impl Backpex.Metric
def query(_query, _select, _repo), do: MyApp.Absences.vacation_balance()

# After
@impl Backpex.Metric
def data(_metric, _query, assigns) do
  MyApp.Absences.vacation_balance(assigns.current_user, assigns.filter_values)
end
```

If an aggregate such as `{:sum, :price}` can express the data, use it instead of `data/3`. The adapter computes it in
the database.

`data/2` of v0.23 is now `c:Backpex.Metric.data/3`. Besides the metric and the assigns, it receives the query of the
index view, which also holds the search (`query.search`). The validated filter values are still in
`assigns.filter_values`. A metric module with `use BackpexWeb, :metric` that still defines `data/2` without `data/3`
doesn't compile. For other metric modules, Backpex raises when it computes the metric.

```elixir
# Before
@impl Backpex.Metric
def data(_metric, assigns), do: MyApp.Absences.vacation_balance(assigns.current_user, assigns.filter_values)

# After
@impl Backpex.Metric
def data(_metric, _query, assigns), do: MyApp.Absences.vacation_balance(assigns.current_user, assigns.filter_values)
```

### Custom adapters

Backpex builds a `Backpex.Query` for every read, and the adapter only runs it. The read callbacks of v0.23 are gone:
`get/4`, `list/4` and `count/4` no longer exist, and neither do the callbacks this version added at first for metrics
and the options of association fields. Implement these callbacks instead:

- `c:Backpex.Adapter.read/1` returns the items of a query: the items at the end of its `:from` (the items of the
  resource, or related items such as the options of an association field), that match its `:filter` and `:search`,
  sorted by `Backpex.Query.sorts/1`, after its `:offset` and up to its `:limit`, with the relationships of its `:load`.
  It replaces `get/4` (a filter on the primary key with a limit of 1) and `list/4`.
- `c:Backpex.Adapter.count/1` returns the number of items of a query.
- `c:Backpex.Adapter.aggregate/1` returns the values of the `:aggregates` of a query, e.g. the data of metrics. Each
  aggregate covers the items of the query that also match its `:where` expression.
- `c:Backpex.Adapter.new_item/2` returns the item for the form of the `:new` action.
- `c:Backpex.Adapter.describe/2` returns the primary key, the fields with their types and the relationships of the
  items of the resource, or of related items at the end of a path, see `Backpex.Adapter.Description`. Backpex checks
  and casts the expressions of queries with it, finds the keys of relationships and tells integer fields from others
  in `Backpex.Filters.Range`.
- `c:Backpex.Adapter.put_assoc/4` puts associated items into a changeset.
- `c:Backpex.Adapter.field_config_schema/0` returns the options your adapter adds to fields. It is optional, and
  `use Backpex.Adapter` defines it from its `:field_config_schema` option.
- `c:Backpex.Adapter.put_field_options/2` is optional. It takes the options your adapter adds to fields into a query,
  as adapters no longer get the fields of the LiveResource.
- `c:Backpex.Adapter.supports?/2` is optional and says which parts of a query your adapter runs itself. Backpex applies
  the others to the items in memory (`Backpex.Query.apply_to/2`), so `count/1` and `aggregate/1` are optional, too.
  `use Backpex.Adapter` takes the parts as its `:supports` option and defaults to all parts. See the
  [custom adapter](custom-adapter.md) guide for an adapter that only returns all items, and `Backpex.Adapters.Memory`
  for an adapter that keeps the items in memory.

The filters of a query are already checked and cast with your `describe/2`, see `Backpex.Expr` for the structs of
expressions. Equal queries read the same items (see `Backpex.Query.key/1`), so the options of association fields are
read once per distinct query and again when their query changes, e.g. when an `:options_filter` depends on a value of
the form.

`delete_all/2` should return `{:error, :foreign_key_violation}` if an item can't be deleted because other data still
references it.

`c:Backpex.Adapter.update_all/3` takes a map of fields and values instead of the updates of `c:Ecto.Repo.update_all/3`,
and returns `{:ok, count}`. Backpex checks the fields with your `describe/2` and casts the values. An adapter that
doesn't support `:insert`, `:update` or `:delete` (see `c:Backpex.Adapter.supports?/2`) makes `Backpex.Authorization`
deny the `:new`, `:edit` or `:delete` actions, so the views hide them.

### Updating many items

`Backpex.Resource.update_all/5` takes the fields to set and their values as a map or keyword list, e.g. for a soft
delete. The updates of `c:Ecto.Repo.update_all/3` raise now:

```elixir
# Before
Backpex.Resource.update_all(items, [set: [deleted_at: now]], assigns, live_resource)

# After
Backpex.Resource.update_all(items, %{deleted_at: now}, assigns, live_resource)
```

### `item_query`, `:select` and `:custom_alias` are gone

No code outside the adapter gets an Ecto query to change anymore. The `item_query` of the `adapter_config` of
`Backpex.Adapters.Ecto` and the `:select` and `:custom_alias` options of fields are replaced by callbacks of the
LiveResource that return expressions (see `Backpex.Expr`) and work with every adapter, see the
[scope and load](scope-and-load.md) and [computed fields](computed-fields.md) guides:

| Before | After |
| --- | --- |
| `where` in the `item_query` | `c:Backpex.LiveResource.scope/1`, e.g. `expr(is_nil(deleted_at))` |
| `preload` in the `item_query` | `c:Backpex.LiveResource.load/1`, e.g. `[proceeding: :module]`; a preload query becomes `Backpex.Query.related/1` |
| `select_merge` in the `item_query`, the `:select` of a field | `c:Backpex.LiveResource.computed/1`, e.g. `full_name: expr(concat([first_name, last_name], " "))` |
| `:select` of an association field and `select_merge` in its `:options_query` | `:computed` of the query of the relationship in `load/1`, which the options get, too |
| `order_by` on a join in the `item_query` | `init_order: %{by: :"contact.last_name", direction: :asc}` |
| a join of a subquery of related items, e.g. their number or the value of the primary one | `Backpex.Expr.aggregate/3` in `computed/1`, e.g. `aggregate(:first, :partners_contacts, value: expr(partner.name), where: expr(primary == true))` |
| joins for a `:select` or under a `:custom_alias` | paths in expressions, e.g. `expr(contact.last_name)` |
| a SQL fragment | `Backpex.Expr.native/3`, with `uses: [:contact]` for the joins of paths |

```elixir
# Before
use Backpex.LiveResource,
  adapter_config: [
    # ...
    item_query: &__MODULE__.item_query/3
  ]

def item_query(query, _live_action, assigns) do
  query
  |> where([user], user.partner_id == ^assigns.current_scope.partner.id)
  |> preload(:contact)
end

def fields do
  [
    full_name: %{
      module: Backpex.Fields.Text,
      label: "Full Name",
      select: dynamic([user: u], fragment("concat(?, ' ', ?)", u.first_name, u.last_name))
    }
  ]
end

# After
import Backpex.Expr

@impl Backpex.LiveResource
def scope(assigns), do: expr(partner_id == ^assigns.current_scope.partner.id)

@impl Backpex.LiveResource
def load(_assigns), do: [:contact]

@impl Backpex.LiveResource
def computed(_assigns), do: [full_name: expr(concat([first_name, last_name], " "))]

def fields do
  [full_name: %{module: Backpex.Fields.Text, label: "Full Name"}]
end
```

The `schema/2` callback of `Backpex.Adapters.Ecto.Field` is gone, as there are no joins under other names anymore.
`c:Backpex.Adapters.Ecto.Field.search_condition/3` receives the join of the association of an association field,
e.g. `:backpex_author`, instead of a binding named after its schema.

The new `:options_filter` option of `Backpex.Fields.BelongsTo`, `Backpex.Fields.HasMany` and
`Backpex.Fields.HasManyThrough` limits the options of the field with an expression, next to the `:options_query` of
the Ecto adapter.

### Custom fields

The options and callbacks of fields that only `Backpex.Adapters.Ecto` used moved to it:

- The `:select` and `:custom_alias` options are gone, see above. An adapter can still add options to fields with
  `c:Backpex.Adapter.field_config_schema/0`.
- The `search_condition/3` callback moved from `Backpex.Field` to `Backpex.Adapters.Ecto.Field`, and `schema/2` is gone.
  If your field implements `search_condition/3`, add `@behaviour Backpex.Adapters.Ecto.Field` and use
  `@impl Backpex.Adapters.Ecto.Field`. `use Backpex.Field` no longer defines it, and the built-in fields no longer
  implement it. The adapter casts searchable columns that are not strings to text (see below), so you can remove a
  `search_condition/3` callback that only does that.
- The `before_changeset/6` callback is now `c:Backpex.Field.before_changeset/5`. It no longer receives the repo, so its
  arguments are `changeset, attrs, metadata, field, assigns`. A field that still defines `before_changeset/6` doesn't
  compile. A field that loaded data with the repo can load the items of an association with
  `Backpex.Resource.list_options/4` and put them into the changeset with `Backpex.Resource.put_assoc/4`, or call the
  repo of your app.

If your field calls one of these functions on a built-in field, e.g. `search_condition/3` of `Backpex.Fields.Number`,
build the condition in your field instead. Code that calls `schema/2` on the module of a field, e.g. to build the
query of an export, raises now. Build the query of the index view with `Backpex.LiveResource.index_query/1` instead:

```elixir
{:ok, items} =
  assigns
  |> Backpex.LiveResource.index_query()
  |> Backpex.Query.unset([:limit, :offset])
  |> Backpex.Resource.read()
```

`use Backpex.Field` no longer imports `Ecto.Query`. If your field imports it only for the callbacks Backpex used to
define, the compiler now warns that the import is unused.

The `:options_query` option of association fields only works with the Ecto adapter. It receives the `Ecto.Query` and
the assigns. Use `:options_filter` for a filter that works with every adapter. Its documentation called the second argument `_field` and showed a function with one
argument, but it always took the assigns as the second argument.

### `Backpex.Fields.BelongsTo` no longer assigns `:queryable`

`Backpex.Fields.BelongsTo` no longer assigns the schema of the association as `:queryable`, and the assigns passed to its
`:options_query` no longer contain it. Check your `render`, `render_form` and `options_query` functions of these fields if
they use it.

### Association fields get no schemas

The Ecto adapter now builds the queries of the options of association fields:

- The query passed to the `:options_query` of `Backpex.Fields.HasMany` only has a named binding while the user searches
  the options, as your `:options_query` may name its own binding. Use a positional binding instead, e.g.
  `&where(&1, [user], user.role == :admin)`.
- `Backpex.Fields.HasManyThrough` still assigns the `:association`, but its `:pivot` and `:child` no longer have a
  `:queryable` key. Check your templates if they read the schemas from it.

### The form runs `before_changeset` on mount

The form of the `:new` and `:edit` actions builds its first changeset through `c:Backpex.Adapter.change/6`, as it does
on every change. So the `c:Backpex.Field.before_changeset/5` callbacks of the fields now also run on mount, and the
`create_changeset` or `update_changeset` function receives a changeset instead of the item. A function that passes its
first argument to `Ecto.Changeset.cast/4` works with both. If your changeset function or `before_changeset/5` callback
expects a struct, or has effects that should only happen on change, update it.

### Search casts columns that are not strings to text

Backpex compared every searchable column to the search string with `ilike`. Only `Backpex.Fields.Number` and
`Backpex.Fields.Currency` cast their column to text first. Now the Ecto adapter casts every column whose type in the
schema is not a string, whatever the field, e.g. the numeric `display_field` of a `Backpex.Fields.BelongsTo` field, and
computed values. String columns are compared as before.

### Deleting items

`Backpex.Resource.delete_all/4` returns `{:error, :foreign_key_violation}` instead of raising when other data still
references an item. If you call it in your own item actions, handle this result:

```elixir
case Backpex.Resource.delete_all(items, socket.assigns, socket.assigns.live_resource, authorize?: false) do
  {:ok, deleted_items} ->
    {:ok, put_flash(socket, :info, "Deleted #{length(deleted_items)} items.")}

  {:error, :foreign_key_violation} ->
    {:ok, put_flash(socket, :error, "The items are still in use.")}
end
```

### Changed functions

- `search_options/3` of `Backpex.LiveResource` is now `Backpex.LiveResource.search_options/2`. It no longer takes the
  schema.
- `list_query/4`, `apply_search/4`, `apply_filters/4` and `apply_criteria/3` of `Backpex.Adapters.Ecto` are gone.
  `Backpex.Adapters.Ecto.ecto_query/1` returns the `Ecto.Query` of a `Backpex.Query`, e.g. to stream the items of an
  export.
- `Backpex.Resource.list/4`, `Backpex.Resource.count/4` and `Backpex.LiveResource.build_criteria/1` are now
  `Backpex.Resource.read/1`, `Backpex.Resource.count/1` and `Backpex.LiveResource.index_query/1`, which build and take
  a `Backpex.Query`.
- The `query` functions of `Backpex.Filters.Boolean`, `Backpex.Filters.Select`, `Backpex.Filters.MultiSelect` and
  `Backpex.Filters.Range` are now their `c:Backpex.Filter.condition/3` callbacks, which return the expression of the
  filter. `maybe_query/2` of `Backpex.Filters.Boolean` and `do_query/3` of `Backpex.Filters.Range` are gone, and so is
  `query/3` of `Backpex.Metrics.Value`.
- The `changeset/3` functions of the built-in filters are their `c:Backpex.Filter.changeset/3` callbacks. They take the
  filter instead of the field and the options or the type of the range.
