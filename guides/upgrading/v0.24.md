# Upgrading to v0.24

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.24.0"}
  ]
end
```

## Select fields are ordered and searched by their labels

The index view orders and searches `Backpex.Fields.Select` fields by the labels of their options instead of the stored
values, so the results match what the user sees, including labels you translate in an `options` function. A search no
longer matches the stored value of an option, only its label. Values without an option are still ordered and searched by
the stored value. Ordering and searching by labels uses PostgreSQL functions, so it requires the `Backpex.Adapters.Ecto`
adapter with a PostgreSQL database.

To resolve the labels, Backpex now also calls the `options` function of a select field when ordering or searching by it,
with all assigns of the index view whatever you set `:context_assigns` to. The assigns of a row are not set then: `:item`
is `nil`, or the `base_schema` of a resource action while one is open, and assigns such as `:value` are missing. An
`options` function that reads the fields of the item or the value raises then:

```diff
  role: %{
    module: Backpex.Fields.Select,
-   options: fn assigns -> role_options(assigns.item.organization) end
+   options: fn assigns -> role_options(assigns.current_scope.organization) end
  }
```

Fields can change how the index view orders and searches them with the new `c:Backpex.Field.order_expression/4` and
`c:Backpex.Field.search_condition/5` callbacks. `use Backpex.Field` defines both with the previous behaviour, so custom
fields keep working. Only a field module that implements the behaviour without `use Backpex.Field` has to implement
them.

If you call `Backpex.Adapters.Ecto.apply_search/4` or `Backpex.Adapters.Ecto.apply_criteria/3` yourself, pass the
assigns as the new last argument, so `options` functions receive them.
