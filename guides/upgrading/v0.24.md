# Upgrading to v0.24

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.24.0"}
  ]
end
```

## The forms of `BelongsTo` and `HasManyThrough` only save options

The `options_query` of `Backpex.Fields.BelongsTo` and `Backpex.Fields.HasManyThrough` only limited the options of the
select, so a crafted request could save any record. The forms now check the submitted records against the options
query, as the form of `Backpex.Fields.HasMany` and the index form of `Backpex.Fields.BelongsTo` already do:

- `BelongsTo` saves an option, no option, or the value the item already has.
- `HasManyThrough` links options and keeps the records the item is already linked to.

Any other record gets the error `"is invalid"`, so a save that went through before can now be refused. This affects
you if your code or your tests submit a record the select doesn't offer, e.g. one beyond a `limit` of the options
query. Widen the `options_query` to every record the field may be set to.

The check only runs for a field that is part of the form and not readonly, so keep validating the value in your
changeset where it matters.

## Forms save only the params of fields an admin may edit

Before v0.24, the form passed every param of the client to the changeset, except the params of readonly fields. A
crafted client could change a value through a field that `can?`, `only` or `except` hides from the admin, or through a
column the LiveResource has no field for, whenever the changeset casts it.

The form now passes only the params of the fields of the current view that `can?` allows and that are not readonly.
Backpex drops every other param before it calls `before_changeset/6` of `Backpex.Field` and the changeset.

A field submits the param of its name by default, e.g. `change[title]`. If a custom field renders inputs under other
names, return all of them from the new `c:Backpex.Field.param_keys/2` callback, or the form drops them:

```elixir
@impl Backpex.Field
def param_keys({name, _field_options}, _assigns) do
  name = Atom.to_string(name)

  [name, name <> "_confirmation"]
end
```

A field whose form submits rows of nested params returns `{key, keys}` for them, and the form keeps only the given keys
in each row. See [Form params](custom-fields.md#form-params).

The same holds for a built-in field with the `render_form` option: if the function renders inputs under other names
than the field's own, the form drops them. There is no field option to add params, so move such a form into a custom
field module that returns them from `param_keys/2`.

The built-in fields return their params already, e.g. `Backpex.Fields.BelongsTo` the foreign key of the association.
`Backpex.Fields.InlineCRUD` passes only the child fields of each row that the admin may edit, so a readonly child field
or one that `can?`, `only` or `except` hides can't be changed through crafted params either.
`Backpex.Fields.HasManyThrough` passes only the primary key, the related item and the `pivot_fields` of each entry, so
map every pivot column the admin sets in `pivot_fields`. `Backpex.Fields.Upload` passes no param of its name, as
`put_upload_change` builds it on the server.

The `visible` option is left out on purpose: it only hides the input, and the form still saves the params of a field
it hides. Use `can?` or `readonly` to keep an admin from changing a field.

If your changeset needs a value that no field of the form submits, set it on the server instead of rendering an input
for it: in the changeset from the `:assigns` of its metadata, or in `c:Backpex.LiveResource.on_item_creating/2` and
`c:Backpex.LiveResource.on_item_updating/2`, which receive the change before it is saved.

`Backpex.Field.drop_readonly_changes/3` now also drops the params a readonly field returns from `param_keys/2`, e.g.
the foreign key of a readonly `Backpex.Fields.BelongsTo` field.
