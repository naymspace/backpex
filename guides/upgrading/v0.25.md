# Upgrading to v0.25

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.25.0"}
  ]
end
```

## `postgrex` is an optional dependency and `phoenix_html_helpers` is gone

Backpex used each of the two packages in one place: `postgrex` to recognize a foreign key violation when deleting
items, `phoenix_html_helpers` to render the hidden inputs of the `Backpex.Fields.HasManyThrough` form. Both places work
without the package now, so Backpex no longer adds them to your application.

Backpex still needs PostgreSQL. An application with an `Ecto.Adapters.Postgres` repository lists `postgrex` itself, as
`mix phx.new` generates it; make sure it is in your `mix.exs`:

```elixir
defp deps do
  [
    {:postgrex, ">= 0.0.0"}
  ]
end
```

If your own code calls `PhoenixHTMLHelpers` and got the package only through Backpex, add it too:

```elixir
defp deps do
  [
    {:phoenix_html_helpers, "~> 1.0"}
  ]
end
```

## Saving an edit reads the item again

Before v0.25, the edit form saved the item it had loaded when it was opened, and `Backpex.Field.handle_index_editable/3`
saved the item the field component had rendered. The `:edit` check of `c:Backpex.LiveResource.can?/3`, the readonly
checks and the changeset therefore saw a record that may have changed, been deleted or left the scope of the
`item_query` since.

Both now read the item again through the adapter right before they save. For the edit form this means:

- A save of an item that was deleted or has left the scope of the `item_query` raises `Backpex.NoResultsError`, and a
  save of an item the admin may no longer edit raises `Backpex.ForbiddenError`. Before, such a save went through, or
  raised an `Ecto.StaleEntryError` for a deleted row.
- The changeset is built on the re-read record, so every field of the form is saved with the value the form shows.
  Before, a field the admin did not touch kept a value that was written to the record while the form was open. Fields
  the form does not contain and fields that are readonly for the re-read record keep their value in the database.
- The `item` assign of the socket that `c:Backpex.LiveResource.on_item_updating/2` and
  `c:Backpex.LiveResource.on_item_updated/2` receive is the re-read item.

See [Saving an edit re-reads the item](../authorization/live-resource-authorization.md#saving-an-edit-re-reads-the-item).

A custom field that saves its inline edits with `Backpex.Field.handle_index_editable/3` now calls the `item_query` of
the adapter config with the assigns of the field component. With a list of `context_assigns`, these only include the
listed assigns, so an `item_query` that reads another assign raises a `KeyError`. Add every assign your `item_query`
reads to `context_assigns`:

```elixir
use Backpex.LiveResource,
  adapter_config: [
    # ...
    item_query: &__MODULE__.item_query/3
  ],
  context_assigns: [:current_scope]

def item_query(query, _live_action, assigns) do
  from p in query, where: p.organization_id == ^assigns.current_scope.organization_id
end
```

Inline edits that the index view saves, i.e. those of fields rendering `Backpex.HTML.Form.index_form/1`, already read
the item again with all assigns of the LiveView and are not affected.
