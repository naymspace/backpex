# Upgrading to v0.20

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.20.0"}
  ]
end
```

## Collapsible Sidebar

The `app_shell` component now ships with a unified collapsible sidebar that replaces the previous split between a mobile drawer and a desktop-only sidebar. **This introduces breaking changes to the sidebar API:**

### `topbar_branding` renamed to `sidebar_branding` and moved into `<:sidebar_branding>`

The branding component has been renamed and belongs in the new `<:sidebar_branding>` slot, which renders above the scrollable navigation, not in the topbar.

Your `<:sidebar>` content itself does not change: `app_shell` still wraps it in the scrollable container and the `<ul>` that `sidebar_item` and `sidebar_section` (which render `<li>` elements) require, so keep placing them directly in the slot.

**Before:**

```heex
<Backpex.HTML.Layout.app_shell ...>
  <:topbar>
    <Backpex.HTML.Layout.topbar_branding />
    <!-- ...other topbar content... -->
  </:topbar>
  <:sidebar>
    <!-- nav items -->
  </:sidebar>
</Backpex.HTML.Layout.app_shell>
```

**After:**

```heex
<Backpex.HTML.Layout.app_shell ...>
  <:topbar>
    <div class="flex-1"></div>
    <!-- ...other topbar content... -->
  </:topbar>
  <:sidebar_branding>
    <Backpex.HTML.Layout.sidebar_branding />
  </:sidebar_branding>
  <:sidebar>
    <!-- nav items, unchanged -->
  </:sidebar>
</Backpex.HTML.Layout.app_shell>
```

The sidebar is a single `<nav>` landmark, so avoid nesting another `<nav>` inside either slot.

### Optional: customize the `--sidebar-width` CSS variable

The sidebar uses a `--sidebar-width` CSS custom property for its width and the main-content shift. It falls back to `16rem`, so no change is required to keep the default width. Define the variable only when you want to customize it:

```css
/* assets/css/app.css */
:root {
  --sidebar-width: 16rem;
}
```

### `sidebar_section` requires an explicit `id`

`Backpex.HTML.Layout.sidebar_section` no longer defaults `id` to `"section"`. The id becomes the suffix of the adapter-backed preference key `global.sidebar_section.<id>` and is also used for `aria-controls`, so two sections without explicit ids would collide and toggle together. Every `sidebar_section` now needs its own unique id. Use only ASCII letters, digits, underscores, and hyphens (`[A-Za-z0-9_-]+`): dots and colons change preference-key segmentation, while quotes and backslashes are unsafe in the hook's selector.

```heex
<Backpex.HTML.Layout.sidebar_section id="blog">
  <:label>Blog</:label>
  <!-- items -->
</Backpex.HTML.Layout.sidebar_section>
```

### New JavaScript hook for sidebar drawer state

A new `BackpexSidebar` hook now manages the sidebar drawer open/close state, while section expand/collapse continues to live in the `BackpexSidebarSections` hook. Section state is no longer read from `localStorage`; it is persisted through `Backpex.Preferences` and mirrored in `sessionStorage` for live navigation. If you register hooks individually rather than spreading `BackpexHooks`, make sure all three hooks are registered: `BackpexSidebar`, `BackpexSidebarSections`, and `BackpexPreferencesHook` (omitting `BackpexPreferencesHook` silently disables preference persistence). If you use the default spread in your `app.js`, no hook-registration change is required.

### Required: wrap your LiveSocket params with `backpexParams`

Backpex now sends the browser's stored preferences in the LiveView connect params, so `mount/3` can render the user's actual columns, metrics, and sidebar state on the **first** render. Update your `app.js`:

```diff
- import { Hooks as BackpexHooks } from 'backpex'
+ import { Hooks as BackpexHooks, backpexParams } from 'backpex'

  const liveSocket = new LiveSocket('/live', Socket, {
-   params: { _csrf_token: csrfToken },
+   params: backpexParams({ _csrf_token: csrfToken }),
    hooks: { ...BackpexHooks }
  })
```

Skip this and preferences written after the websocket connects — a hidden column, a hidden metrics panel — revert as soon as the user navigates to another resource. Backpex logs a console warning when it detects the params are missing. Keep it a function, not a plain object: LiveView re-evaluates it on every join, which is what keeps the values current.

### Sidebar breakpoint raised from `md` to `lg`

The sidebar now switches between the mobile drawer and the inline desktop layout at the `lg` breakpoint (1024 px) instead of `md` (768 px). Tablets between 768–1023 px will see the mobile drawer where they previously saw the inline sidebar. The breakpoint is read from the `--breakpoint-lg` CSS custom property (Tailwind v4 default `64rem`); customize it in your Tailwind config if needed.

### Translations

The following translation msgids have been renamed for the new sidebar. Update your `.po` files to use the new msgids:

| Removed msgid | Replacement msgid |
|---|---|
| `Main desktop navigation` | `Main navigation` |
| `Main mobile navigation` | `Main navigation` (merged) |
| `Toggle menu` | `Toggle sidebar` |

## User Preferences System Overhaul

> #### Warning {: .warning}
>
> `app_shell` now declares `socket` as required. The preference-related component attributes have defaults, so omitting `sidebar_open`, `preferences_manifest`, or `sidebar_section_states` may render successfully while losing restored state or the fast-reload overlay. After each step below, verify in the browser that the feature works (toggle theme, columns, metrics, and sidebar state; navigate live; then reload).

This version introduces a unified preference system. User preferences (theme, desktop sidebar state, column visibility, etc.) are server-rendered from a configurable storage backend on every request. A short-lived pending cookie and an opt-in per-tab mirror cover writes that the server-side session snapshot cannot see yet; the limitations of those carriers are described below.

Backpex ships with a Phoenix-session adapter out of the box, so no action is needed to keep preferences in the session. Route individual prefixes to a scoped database adapter when you outgrow the ~4KB cookie ceiling or need preferences to follow a user across devices or stay isolated between tenants. See the [User Preferences guide](../live_resource/user-preferences.md) for adapter recipes and the opt-in persistence flag for ordering / filters / columns / metrics.

### Preferences: adapter architecture

- **Terminology.** Storage is pluggable (session, ETS, Ecto, ...), so the
  subsystem is called "preferences" rather than "cookie-based preferences."
  The JS property exposed to hooks is `BackpexPreferences.endpointPath`.
- **Default behavior.** With no config, every key routes to
  `Backpex.Preferences.Adapters.Session`, so existing apps need no changes
  to store new preferences. Once an `:adapters` list is configured there is
  no implicit Session fallback: include an explicit `:default` route unless
  every possible key is covered.
- **Route a prefix to your database.** Configure the built-in Ecto adapter (or
  implement `Backpex.Preferences.Adapter` for a custom backend) and add the route:

  ```elixir
  config :backpex, Backpex.Preferences,
    adapters: [
      {"resource.*", Backpex.Preferences.Adapters.Ecto,
       repo: MyApp.Repo,
       schema: MyApp.Preferences.Preference,
       scope_fields: [:user_id, :tenant_id]},
      {:default,     Backpex.Preferences.Adapters.Session, []}
    ],
    scope: {MyAppWeb.PreferencesScope, :resolve, []}
  ```

  Backpex ships the adapter; you supply the migration and schema. Walkthrough
  in the [User Preferences guide](../live_resource/user-preferences.md).
- **Scope resolver.** A database-backed route requires one application-wide
  `:scope` resolver. It returns a non-empty atom-keyed map such as
  `%{user_id: user.id, tenant_id: tenant.id}`. Each Ecto route selects its
  namespace columns with `scope_fields:` and its unique index must contain
  `scope_fields ++ [:key]` in the same order.
- **Browser namespace callback.** Custom adapters may implement the optional
  `c:Backpex.Preferences.Adapter.client_namespace/2` callback when they use only
  part of the resolved application scope or ignore it entirely. Return a stable
  term identifying exactly the namespace in which the adapter stores values.
  Backpex signs it before it reaches the browser. Adapters that omit the
  callback conservatively use the complete scope and their route options.
- **Per-resource module keys.** Internal
  `resource:<Module>:<suffix>` keys use `:` as a separator so module-name
  dots don't create accidental path segments.
- **New `persist:` option on `use Backpex.LiveResource`.** Opt in to
  persisting ordering, filters, column visibility, or metric visibility
  through the preferences layer:

  ```elixir
  use Backpex.LiveResource,
    adapter_config: [...],
    persist: [:order, :filters, :columns, :metrics]
  ```

  Default is `[]`, which keeps ordering and filters in the URL and column
  and metric visibility in-memory. In v0.19, both column visibility and
  metric visibility were stored in the session without an opt-in. Add
  `persist: [:columns, :metrics]` to each resource where both toggles should
  continue to survive reloads (or select just the behavior you want).

### Existing preference state is not migrated

The new Session adapter reads only the `"backpex_preferences"` session key.
It does not read or migrate the v0.19 `"backpex"` session tree, and the new
hooks do not read the old `localStorage` entries. Upgrading therefore resets
existing UI choices unless the host application performs its own migration.

| v0.19 state | v0.20 behavior |
|---|---|
| `session["backpex"]["theme"]` and `localStorage["backpexTheme"]` | Not read; the configured/default theme is used until the user selects one again. |
| `session["backpex"]["column_toggle"]` | Not read; columns use their configured defaults. Add `persist: [:columns]` for future changes to survive reloads. |
| `session["backpex"]["metric_visibility"]` | Not read; metrics start visible. Add `persist: [:metrics]` for future changes to survive reloads. |
| `localStorage["sidebar-section-<id>"]` | Not read; unknown sections start open and future changes use `global.sidebar_section.<id>` through the configured preference adapter. |

Remove the legacy `localStorage` entries when convenient. If preserving
existing session choices is important, translate the old tree to the new keys
inside your application before clearing it; Backpex does not ship an automatic
migration because custom session and scope lifecycles differ between hosts.

### Preferences: browser-side changes

None of these require action in your app, but they are observable.

- **New cookie: `backpex_prefs`.** Preference writes are POSTed
  asynchronously, so a reload fired right after a toggle can carry a session
  cookie that is still one round-trip behind — and the first render would show
  the pre-toggle state. Backpex now writes the not-yet-acknowledged values into
  a short-lived, JS-written cookie (`path=/`, `SameSite=Lax`, `max-age=300`,
  `Secure` over HTTPS, not `HttpOnly`) that the disconnected mount reads, so the
  first paint can reflect that pending write. Each entry deletes itself as soon
  as its POST responds; the cookie is absent the rest of the time. Its value is
  a versioned envelope, `{"version": 1, "values": {key: {"token": "...", "value":
  value}}}`. Every entry carries the signed namespace token of the adapter route
  that owns its key. A session-backed sidebar value can therefore survive a
  tenant switch while a tenant-scoped database value is discarded (see the
  [User Preferences guide](../live_resource/user-preferences.md#scoping-browser-carried-values-per-adapter)).
  The encoded cookie is capped at 3072 bytes: Backpex evicts the oldest pending
  entries until it fits, and skips a single entry that cannot fit. It also skips
  the cookie when no signed preferences manifest is available. In either case a reload
  inside the POST round trip may briefly render the stored value.
  If you run a cookie-consent banner, note that `backpex_prefs` is designed as a
  strictly functional cookie: route tokens are keyed digests rather than raw
  user or tenant ids, and the cookie is only an input to a render. Confirm the
  classification required by your own jurisdiction and consent policy.
- **`BackpexPreferences.connectParams()` now sends the mirror on the first
  join** instead of `{}`, so the connected render agrees with the paint the dead
  render just produced. `backpexParams` picks this up automatically; if you
  hand-rolled the connect params, switch to `backpexParams`.
- **New JS API:** `BackpexPreferences.isPending(key)` — whether this browser
  holds a write the server has not acknowledged. Check it before adopting a
  server-rendered attribute in your own hook.
- **`global.theme` is now mirrored to sessionStorage**, like every other
  server-rendered preference, so it appears under the route-token-prefixed
  `backpex.prefs.<route token>.<key>` keys and in the per-entry-token `backpex_prefs`
  connect-param envelope.
- **The `BackpexSidebarSections` hook no longer writes `data-section-open`.**
  That attribute is server-owned now and is the baseline the hook reconciles
  against. Anything keying CSS or a test off the hook-written value must key off
  `aria-expanded` instead.
- **Client-supplied preference values are shape-checked.**
  `Backpex.Preferences.Context.put_client/2` now drops entries whose value fails
  `Backpex.Preferences.Keys.valid_value?/2`, on both client carriers (the cookie
  and the connect params). A render must not raise on browser input — `not
  "false"` does — so a wrong-typed value falls back to the stored one instead of
  taking the page down. Only keys Backpex owns are checked; values for your own
  keys pass through, so render them defensively.

### Breaking Changes

#### 1. Remove `Backpex.ThemeSelectorPlug`

The `Backpex.ThemeSelectorPlug` has been removed. Theme preferences are now handled by `Backpex.InitAssigns`.

**Before:**
```elixir
# router.ex
pipeline :browser do
  ...
  plug Backpex.ThemeSelectorPlug
end
```

**After:**
```elixir
# router.ex
pipeline :browser do
  ...
  # Remove the ThemeSelectorPlug line - it's no longer needed
end
```

#### 2. Update root layout theme attribute

Change the theme assign name from `@theme` to `@current_theme`:

**Before:**
```heex
<html data-theme={assigns[:theme] || "light"}>
```

**After:**
```heex
<html data-theme={assigns[:current_theme] || "light"}>
```

#### 3. Update theme_selector component

The `theme_selector` component now requires `current_theme` instead of relying on localStorage:

**Before:**
```heex
<Backpex.HTML.Layout.theme_selector
  socket={@socket}
  themes={[{"Light", "light"}, {"Dark", "dark"}]}
/>
```

**After:**
```heex
<Backpex.HTML.Layout.theme_selector
  current_theme={@current_theme}
  themes={[{"Light", "light"}, {"Dark", "dark"}]}
/>
```

> #### Custom layouts: `theme_selector` is no longer self-contained {: .warning}
>
> In v0.19 the theme selector carried its own endpoint (`data-cookie-path`), so
> it worked in any layout. In v0.20 every preference write — theme, sidebar
> state, sidebar sections, and LiveResource writes — goes through one element
> that carries the endpoint, and `app_shell/1` is what renders it.
>
> **If your layout uses `Backpex.HTML.Layout.app_shell/1`, there is nothing to
> do.** If it does not, render the element yourself, once per page, or every
> preference write is silently dropped: the UI still updates optimistically, so
> nothing looks broken until the next reload reverts it, and the only signal is
> a console warning.
>
> ```heex
> <Backpex.HTML.Layout.preferences_root
>   socket={@socket}
>   preferences_manifest={@preferences_manifest}
> />
> ```
>
> Note this is not caught at compile time: the old `theme_selector socket={@socket}`
> call site still compiles and renders.

#### 4. Update app_shell component

The `app_shell` component now requires `socket`. Its `sidebar_open` and
`preferences_manifest` attributes are optional (`true` and `nil` by default),
but pass the assigns from `Backpex.InitAssigns` to restore the desktop sidebar
state and safely carry unacknowledged writes across a fast reload:

**Before:**
```heex
<Backpex.HTML.Layout.app_shell fluid={@fluid?} live_resource={@live_resource}>
```

**After:**
```heex
<Backpex.HTML.Layout.app_shell
  socket={@socket}
  fluid={@fluid?}
  live_resource={@live_resource}
  sidebar_open={@sidebar_open}
  preferences_manifest={@preferences_manifest}
>
```

`@preferences_manifest` contains one opaque, keyed namespace token per configured adapter route and is assigned by `Backpex.InitAssigns`. Backpex renders it into the page so the browser can retain values whose actual storage namespace is still compatible and discard only those whose namespace changed. Omitting the attribute is safe (Backpex then ignores browser overlays) but costs you correct state across live navigation and the correct first paint after a toggle-and-reload inside the POST's round trip.

#### 5. Update sidebar_section component

Pass `sidebar_section_states` explicitly, as in the **After** example below.
`sidebar_section/1` is a function component, so an omitted attribute does not
inherit the surrounding `@sidebar_section_states` assign — it defaults to `%{}`,
every section server-renders open, and the browser hook then seeds itself from
that markup, so the user's collapsed sections are lost rather than merely
flashed. The other required breaking change is the unique, selector-safe `id`
described above.

**Before:**
```heex
<Backpex.HTML.Layout.sidebar_section id="blog">
  <:label>Blog</:label>
  ...
</Backpex.HTML.Layout.sidebar_section>
```

**After:**
```heex
<Backpex.HTML.Layout.sidebar_section id="blog" sidebar_section_states={@sidebar_section_states}>
  <:label>Blog</:label>
  ...
</Backpex.HTML.Layout.sidebar_section>
```

#### 6. Remove setStoredTheme call

If you were calling `BackpexHooks.BackpexThemeSelector.setStoredTheme()` in your `app.js`, you can remove it. The server now renders the correct theme on initial page load, so this workaround is no longer needed.

**Before:**
```javascript
import { Hooks as BackpexHooks } from 'backpex';
// ...
BackpexHooks.BackpexThemeSelector.setStoredTheme()
```

**After:**
```javascript
import { Hooks as BackpexHooks } from 'backpex';
// Remove the setStoredTheme() call
```

#### 7. Replace the cookie form protocol with preference writes

`Backpex.Router.cookie_path/1` has been renamed to
`Backpex.Router.preferences_path/1`. The HTTP route generated by
`backpex_routes/0` was also renamed from `/backpex_cookies` to
`/backpex_preferences`.

This is not a helper-only rename. The old endpoint accepted HTML forms such as
`select_theme`, `toggle_columns`, and `toggle_metrics`, then redirected. The new
endpoint accepts the preference payload shapes `{"key": ..., "value": ...}` or
`{"preferences": [...]}` and returns JSON. Renaming an old form action while
leaving its fields intact returns `400 {"ok": false, "error": "missing
key/value"}`.

**Before (no longer supported):**
```heex
<form action={Backpex.Router.cookie_path(@socket)} method="post">
  <input type="hidden" name="select_theme" value="dark" />
  <button>Dark</button>
</form>
```

**After (browser-side custom control):**
```javascript
import { BackpexPreferences } from 'backpex'

BackpexPreferences.set('global.theme', 'dark', { mirror: 'session' })
```

For server-originated LiveView controls, use
`Backpex.Preferences.put(socket, key, value, mirror: :session)`. For a custom
HTTP client, POST one of the documented JSON payloads to
`Backpex.Router.preferences_path/1` with the normal Phoenix CSRF header. See the
[endpoint contract](../live_resource/user-preferences.md#http-endpoint-contract).

When the preferences route has dynamic segments, or the router contains more
than one preferences route, pass a concrete endpoint to the layout so writes
use the same scope as reads:

```heex
<Backpex.HTML.Layout.app_shell
  socket={@socket}
  preferences_manifest={@preferences_manifest}
  preferences_path={~p"/tenants/#{@current_scope.tenant.id}/backpex_preferences"}
>
  ...
</Backpex.HTML.Layout.app_shell>
```

#### 8. Default ordering follows `primary_key`

When `init_order` is omitted, the index now orders ascending by the
LiveResource's configured `primary_key`, rather than always ordering by `:id`.
Resources that use the default `primary_key: :id` are unchanged. If a resource
sets another primary key but intentionally sorted by `:id`, configure that
choice explicitly with `init_order: %{by: :id, direction: :asc}`.

### New Assigns from Backpex.InitAssigns

The `Backpex.InitAssigns` hook now provides these additional assigns:

| Assign | Type | Description |
|--------|------|-------------|
| `@current_theme` | string | The user's selected theme |
| `@sidebar_open` | boolean | Whether the sidebar is open (desktop) |
| `@sidebar_section_states` | map | Map of section IDs to open/closed state |
| `@preferences_manifest` | map \| nil | Signed adapter-route namespace manifest; pass it to `app_shell` |

These assigns are populated through the configured preference adapters and the
validated client overlay. With the default adapter the stored values live in the
Phoenix session.

### Benefits

- **Server-rendered saved state**: The initial state comes from the configured adapter; pending client writes are overlaid when their bounded browser carriers are available
- **Consistent behavior**: All preferences use the same storage mechanism
- **Simplified setup**: No need for separate plugs or localStorage workarounds
