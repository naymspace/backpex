# Upgrading to v0.23

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.23.0"}
  ]
end
```

## `NULL` values are ordered by the database default

Before v0.23, Backpex ordered every column with `ASC NULLS FIRST` or `DESC NULLS LAST`. A regular index (including the
primary key) can't serve these orders, so the database sorted the whole table on every page load of the index view,
even for the default order by primary key. On large tables this is slow and writes temporary files, especially on later
pages.

Backpex now uses plain `ASC` and `DESC` and leaves `NULL` values to the database. In PostgreSQL, `NULL` values now come
last in ascending and first in descending order. Columns without `NULL` values order the same as before.

To keep the old order, set the new `order_nulls` option to `:smallest`, on the LiveResource or on a single field:

```elixir
use Backpex.LiveResource,
  # ...other options
  order_nulls: :smallest
```

```elixir
published_at: %{
  module: Backpex.Fields.DateTime,
  label: "Published at",
  order_nulls: :smallest
}
```

`order_nulls` also accepts `:first` and `:last` for `NULL` values in a fixed place in both directions. Every value except
`:default` needs a matching index on large tables (for `:smallest`:
`create index(:posts, ["published_at NULLS FIRST"])`). See [NULL Values](../live_resource/ordering.md#null-values) in
the ordering guide.

Ordering by the `primary_key` always uses plain `ASC` and `DESC`.

If you have a custom adapter, the order criteria passed to `list/4` now has a `:nulls` key (`:default`, `:first`,
`:last` or `:smallest`).
