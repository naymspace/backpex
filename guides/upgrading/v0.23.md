# Upgrading to v0.23

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.23.0"}
  ]
end
```

## `NULL` values are ordered by the database default

Before v0.23, Backpex ordered every column with `ASC NULLS FIRST` or `DESC NULLS LAST`. A regular index (including the
primary key) can't serve these orders, so the database sorted the whole table on every page load of the index view,
even for the default order by primary key. On large tables this is slow and writes temporary files, especially on later
pages.

Backpex now uses plain `ASC` and `DESC` and leaves `NULL` values to the database. In PostgreSQL, `NULL` values now come
last in ascending and first in descending order. Columns without `NULL` values order the same as before.

To keep the old order, set the new `order_nulls` option to `:smallest`, on the LiveResource or on a single field:

```elixir
use Backpex.LiveResource,
  # ...other options
  order_nulls: :smallest
```

```elixir
published_at: %{
  module: Backpex.Fields.DateTime,
  label: "Published at",
  order_nulls: :smallest
}
```

`order_nulls` also accepts `:first` and `:last` for `NULL` values in a fixed place in both directions. Every value except
`:default` needs a matching index on large tables (for `:smallest`:
`create index(:posts, ["published_at NULLS FIRST"])`). See [NULL Values](../live_resource/ordering.md#null-values) in
the ordering guide.

Ordering by the `primary_key` always uses plain `ASC` and `DESC`.

If you have a custom adapter, the order criteria passed to `list/4` now has a `:nulls` key (`:default`, `:first`,
`:last` or `:smallest`).

## Data access goes through the adapter

Backpex is Ecto-first, but outside of `Backpex.Adapters.Ecto` it no longer builds queries, calls the repo or inspects
schemas. The views, fields and metrics read and write data through `Backpex.Adapter` callbacks, mostly via
`Backpex.Resource`. If you use the Ecto adapter and the built-in fields, check the sections on `Backpex.Fields.BelongsTo`,
search and deleting items.

### Custom adapters

If you have a custom adapter, implement the new callbacks:

- `c:Backpex.Adapter.metric/5` returns the data of a metric.
- `c:Backpex.Adapter.new_item/2` returns the item for the form of the `:new` action.
- `c:Backpex.Adapter.association/2` returns an association of the resource.
- `c:Backpex.Adapter.list_options/4` and `c:Backpex.Adapter.count_options/4` return the items an association field can
  select. `c:Backpex.Adapter.list_options_by_key/4` is optional.
- `c:Backpex.Adapter.put_assoc/4` puts associated items into a changeset.

The criteria passed to `list/4` and `count/4` changed:

- The searchable fields in the `:search` criteria no longer have a `:queryable` key.
- The `:order` criteria no longer has a `:schema` key. Its `:field_name` key holds the name of the field that is ordered
  by, or `nil`.

`delete_all/2` should return `{:error, :foreign_key_violation}` if an item can't be deleted because other data still
references it.

### Custom fields

`c:Backpex.Field.schema/2` and `c:Backpex.Field.search_condition/3` are now optional, and only `Backpex.Adapters.Ecto`
calls them. `use Backpex.Field` no longer defines them, and the built-in fields no longer implement them.

- For a field whose `c:Backpex.Field.association?/1` returns `true`, the adapter uses the schema of the association.
  You can remove a `schema/2` callback that only returns it.
- The adapter casts searchable columns that are not strings to text (see below). You can remove a
  `search_condition/3` callback that only does that.

If your field calls one of these functions on a built-in field, e.g. `search_condition/3` of `Backpex.Fields.Number`,
build the condition in your field instead.

### `Backpex.Fields.BelongsTo` no longer assigns `:queryable`

`Backpex.Fields.BelongsTo` no longer assigns the schema of the association as `:queryable`, and the assigns passed to its
`:options_query` no longer contain it. Check your `render`, `render_form` and `options_query` functions of these fields if
they use it.

### Search casts columns that are not strings to text

Backpex compared every searchable column to the search string with `ilike`. Only `Backpex.Fields.Number` and
`Backpex.Fields.Currency` cast their column to text first. Now the Ecto adapter casts every column whose type in the
schema is not a string, whatever the field, e.g. the numeric `display_field` of a `Backpex.Fields.BelongsTo` field. String
columns are compared as before.

### Deleting items

`Backpex.Resource.delete_all/4` returns `{:error, :foreign_key_violation}` instead of raising when other data still
references an item. If you call it in your own item actions, handle this result:

```elixir
case Backpex.Resource.delete_all(items, socket.assigns, socket.assigns.live_resource, authorize?: false) do
  {:ok, deleted_items} -> # ...
  {:error, :foreign_key_violation} -> # ...
end
```

### Changed functions

- `search_options/3` of `Backpex.LiveResource` is now `Backpex.LiveResource.search_options/2`. It no longer takes the
  schema.
- `apply_criteria/3` of `Backpex.Adapters.Ecto` is now `Backpex.Adapters.Ecto.apply_criteria/4`. It takes the schema as
  the last argument.
