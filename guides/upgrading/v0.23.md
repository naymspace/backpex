# Upgrading to v0.23

## Bump Your Deps

Update Backpex to the latest version:

```elixir
defp deps do
  [
    {:backpex, "~> 0.23.0"}
  ]
end
```

## `NULL` values are ordered by the database default

Before v0.23, Backpex ordered every column with `ASC NULLS FIRST` or `DESC NULLS LAST`. A regular index (including the
primary key) can't serve these orders, so the database sorted the whole table on every page load of the index view,
even for the default order by primary key. On large tables this is slow and writes temporary files, especially on later
pages.

Backpex now uses plain `ASC` and `DESC` and leaves `NULL` values to the database. In PostgreSQL, `NULL` values now come
last in ascending and first in descending order. Columns without `NULL` values order the same as before.

To keep the old order, set the new `order_nulls` option to `:smallest`, on the LiveResource or on a single field:

```elixir
use Backpex.LiveResource,
  # ...other options
  order_nulls: :smallest
```

```elixir
published_at: %{
  module: Backpex.Fields.DateTime,
  label: "Published at",
  order_nulls: :smallest
}
```

`order_nulls` also accepts `:first` and `:last` for `NULL` values in a fixed place in both directions. Every value except
`:default` needs a matching index on large tables (for `:smallest`:
`create index(:posts, ["published_at NULLS FIRST"])`). See [NULL Values](../live_resource/ordering.md#null-values) in
the ordering guide.

Ordering by a primary key column of the schema always uses plain `ASC` and `DESC`.

If you have a custom adapter, the order criteria passed to `list/4` now has a `:nulls` key (`:default`, `:first`,
`:last` or `:smallest`). It also holds the configured value for a primary key column. `Backpex.Adapters.Ecto` uses the
database default for these columns.

## Texts for every upload error

Before v0.23, the form of an upload field crashed with a `FunctionClauseError` on any upload error other than
`:too_large`, `:too_many_files` and `:not_accepted`, for example when the browser's upload to S3 failed
(`:external_client_failure`) or an `external` function returned `{:error, meta, socket}`. Backpex now shows a text for
every error. If you translate Backpex's texts, add translations for the new upload texts in `backpex.pot`.

A custom upload field can give its own texts with the new optional callback `c:Backpex.Field.upload_error/4`. It's
called on the field's module, so it also works for a field that delegates `render_form/1` to `Backpex.Fields.Upload`.
It gets every error, so delegate the ones your field doesn't handle to `Backpex.Fields.Upload.upload_error/4`:

```elixir
@impl Backpex.Field
def upload_error(_field, :too_large, upload, _assigns) do
  Backpex.translate_error({"must be at most %{count} bytes", count: upload.max_file_size})
end

def upload_error(field, error, upload, assigns) do
  Backpex.Fields.Upload.upload_error(field, error, upload, assigns)
end
```

Fields without the callback keep the texts of `Backpex.Fields.Upload`, so nothing changes for them.

## Data access goes through the adapter

Backpex is Ecto-first, but outside of `Backpex.Adapters.Ecto` it no longer builds queries, calls the repo or inspects
schemas. The views, fields, filters and metrics read and write data through `Backpex.Adapter` callbacks, mostly via
`Backpex.Resource`. Filters return conditions and metrics name an aggregate, which the adapter turns into queries.
Options and callbacks that take Ecto queries moved to the Ecto adapter.

If you use the Ecto adapter and the built-in fields, check the sections on filters, metrics, `Backpex.Fields.BelongsTo`,
search and deleting items.

### Filters return conditions

Filters no longer build queries. The `query/4` callback of `Backpex.Filter` is replaced by
`c:Backpex.Filter.condition/3`. It returns a condition, such as `{:==, :status, "open"}`, which the adapter turns into a
query. See `t:Backpex.Filter.condition/0` for all conditions. The built-in filters already return conditions. If your
filter uses a built-in filter and overrides its `query/4`, override `condition/3` instead. A filter that still defines
`query/4` doesn't compile.

`use Backpex.Filters.Boolean` and the other built-in filters no longer import `Ecto.Query`, and neither does
`use BackpexWeb, :filter`. Add `import Ecto.Query` to your filters that use it, e.g. to load their options. Without it,
a `dynamic([post], ...)` expression doesn't compile, e.g. with `undefined variable "post"`.

The predicates of a `Backpex.Filters.Boolean` filter are conditions. `Ecto.Query.dynamic/2` expressions still work with
the Ecto adapter, but conditions work with every adapter:

```elixir
# Before
%{label: "Published", key: "published", predicate: dynamic([x], x.published)}

# After
%{label: "Published", key: "published", predicate: {:==, :published, true}}
```

Replace the `query/4` callback of your custom filters with `condition/3`:

```elixir
# Before
@impl Backpex.Filter
def query(query, attribute, value, _assigns) do
  where(query, [x], field(x, ^attribute) >= ^value)
end

# After
@impl Backpex.Filter
def condition(field, value, _assigns), do: {:>=, field, value}
```

If a filter needs more than the conditions of Backpex, e.g. a fragment of SQL, return an `Ecto.Query.dynamic/2`
expression. Such a filter only works with the Ecto adapter. A filter can't join tables or select distinct items anymore,
as the adapter decides how to join, order and paginate the items. Replace a join with a subquery:

```elixir
# Before
@impl Backpex.Filter
def query(query, _attribute, tag_ids, _assigns) do
  query
  |> join(:left, [post], t in assoc(post, :tags), as: :tag)
  |> where([tag: t], t.id in ^tag_ids)
  |> distinct([post], post.id)
end

# After
@impl Backpex.Filter
def condition(_field, tag_ids, _assigns) do
  tagged_posts = from(p in Post, join: t in assoc(p, :tags), where: t.id in ^tag_ids, select: p.id)

  dynamic([post], post.id in subquery(tagged_posts))
end
```

With the Ecto adapter, the `distinct` of such a join also sorted the items by their primary key first, so the order the
user selected didn't apply while the filter was active. The subquery keeps the order.

Tests that call `query/4` of a filter can call `condition/3` and check the condition, or apply the filter to a query
with `Backpex.Adapters.Ecto.apply_filters/4`:

```elixir
Post
|> from(as: ^Backpex.Adapters.Ecto.name_by_schema(Post))
|> Backpex.Adapters.Ecto.apply_filters(%{status: "draft"}, [status: %{module: MyAppWeb.Filters.Status}], %{})
|> Repo.all()
```

Name the binding as the adapter does, as in the example, if a condition of the filter uses a named binding such as
`dynamic([post: p], ...)`. Without it, the query raises with `unknown bind name`.

### Metrics name an aggregate

`Backpex.Metrics.Value` takes an `:aggregate`, such as `{:sum, :likes}`, and an optional `:where` condition. Its
`:select` expression still works with the Ecto adapter, but an aggregate works with every adapter:

```elixir
# Before
total_likes: %{module: Backpex.Metrics.Value, label: "Total likes", select: dynamic([p], sum(p.likes))}

# After
total_likes: %{module: Backpex.Metrics.Value, label: "Total likes", aggregate: {:sum, :likes}}
```

See `Backpex.Metric` for all aggregates. `use BackpexWeb, :metric` no longer imports `Ecto.Query`.

The `query/3` callback of `Backpex.Metric` is gone. A metric module that gets its data in another way implements
`c:Backpex.Metric.data/3` instead. Backpex calls it instead of the adapter, with the metric, the criteria of the index
view and its assigns. The criteria hold the search under `:search` and the values and configurations of the active
filters under `:filter_values` and `:filter_configs`. A metric module with `use BackpexWeb, :metric` that still defines
`query/3` without `data/3` doesn't compile. For other metric modules, Backpex raises when it computes the metric.

`query/3` received a query that the `item_query`, the search and the filters already limited. `data/3` receives the
criteria instead of a query. To compute the data from the items of the index view, pass the criteria to
`Backpex.Resource.list/4`. The adapter applies the `item_query`, the search and the filters, as it did for `query/3`:

```elixir
# Before
@impl Backpex.Metric
def query(query, _select, repo) do
  query |> repo.all() |> Enum.map(&MyApp.Orders.total/1) |> Enum.sum()
end

# After
@impl Backpex.Metric
def data(_metric, criteria, assigns) do
  {:ok, orders} = Backpex.Resource.list(criteria, assigns.fields, assigns, assigns.live_resource)

  orders |> Enum.map(&MyApp.Orders.total/1) |> Enum.sum()
end
```

A metric that reads its data elsewhere, e.g. from a function of your context module, has to limit the data itself, e.g.
to the items the current user may see:

```elixir
# Before
@impl Backpex.Metric
def query(_query, _select, _repo), do: MyApp.Absences.vacation_balance()

# After
@impl Backpex.Metric
def data(_metric, criteria, assigns) do
  MyApp.Absences.vacation_balance(assigns.current_user, criteria[:filter_values])
end
```

If an aggregate such as `{:sum, :price}` can express the data, use it instead of `data/3`. The adapter computes it in
the database.

### Custom adapters

If you have a custom adapter, implement the new callbacks:

- `c:Backpex.Adapter.metric/5` returns the data of a metric, the `:aggregate` of the metric for the items that match
  its `:where` condition. It gets the criteria of `count/4` and ignores `:order`, `:pagination` and `:limit`. Backpex
  calls `c:Backpex.Metric.data/3` instead if the module of the metric implements it.
- `c:Backpex.Adapter.new_item/2` returns the item for the form of the `:new` action.
- `c:Backpex.Adapter.association/2` returns an association of the resource.
- `c:Backpex.Adapter.list_options/4` and `c:Backpex.Adapter.count_options/4` return the items an association field can
  select. `c:Backpex.Adapter.list_options_by_key/4` is optional.
- `c:Backpex.Adapter.put_assoc/4` puts associated items into a changeset.
- `c:Backpex.Adapter.field_config_schema/0` returns the options your adapter adds to fields. It is optional, and
  `use Backpex.Adapter` defines it from its `:field_config_schema` option.

The criteria passed to `list/4` and `count/4` changed:

- Apply the condition of each filter (`c:Backpex.Filter.condition/3`) instead of calling its `query/4` callback.
- The searchable fields in the `:search` criteria no longer have a `:queryable` key.
- The `:order` criteria no longer has a `:schema` key. Its `:field_name` key holds the name of the field that is ordered
  by, or `nil`. Its `:nulls` key holds the configured value for the primary key, too. `Backpex.Adapters.Ecto` ignores
  it for the primary key.

`delete_all/2` should return `{:error, :foreign_key_violation}` if an item can't be deleted because other data still
references it.

### Custom fields

The options and callbacks of fields that only `Backpex.Adapters.Ecto` used moved to it:

- The Ecto adapter adds the `:select` and `:custom_alias` options to fields (see
  `c:Backpex.Adapter.field_config_schema/0`). Nothing changes for your LiveResources, but the child fields of
  `Backpex.Fields.InlineCRUD` no longer accept them.
- The `schema/2` and `search_condition/3` callbacks moved from `Backpex.Field` to `Backpex.Adapters.Ecto.Field`. If your
  field implements them, add `@behaviour Backpex.Adapters.Ecto.Field` and use `@impl Backpex.Adapters.Ecto.Field`.
  `use Backpex.Field` no longer defines them, and the built-in fields no longer implement them.
  - For a field whose `c:Backpex.Field.association?/1` returns `true`, the adapter uses the schema of the association.
    You can remove a `schema/2` callback that only returns it.
  - The adapter casts searchable columns that are not strings to text (see below). You can remove a
    `search_condition/3` callback that only does that.
- The `before_changeset/6` callback is now `c:Backpex.Field.before_changeset/5`. It no longer receives the repo, so its
  arguments are `changeset, attrs, metadata, field, assigns`. A field that still defines `before_changeset/6` doesn't
  compile. A field that loaded data with the repo can load the items of an association with
  `Backpex.Resource.list_options/4` and put them into the changeset with `Backpex.Resource.put_assoc/4`, or call the
  repo of your app.

If your field calls one of these functions on a built-in field, e.g. `search_condition/3` of `Backpex.Fields.Number`,
build the condition in your field instead. Code that calls `schema/2` on the module of a field, e.g. to build the
criteria of an export, raises now. Build the criteria with `Backpex.LiveResource.build_criteria/1` instead:

```elixir
criteria =
  assigns
  |> Backpex.LiveResource.build_criteria()
  |> Keyword.delete(:pagination)

Backpex.Resource.list(criteria, fields, assigns, live_resource)
```

`use Backpex.Field` no longer imports `Ecto.Query`. If your field imports it only for the callbacks Backpex used to
define, the compiler now warns that the import is unused.

The `:options_query` option of association fields receives the query of the adapter, an `Ecto.Query` for the Ecto
adapter, and the assigns. Its documentation called the second argument `_field` and showed a function with one
argument, but it always took the assigns as the second argument.

### `Backpex.Fields.BelongsTo` no longer assigns `:queryable`

`Backpex.Fields.BelongsTo` no longer assigns the schema of the association as `:queryable`, and the assigns passed to its
`:options_query` no longer contain it. Check your `render`, `render_form` and `options_query` functions of these fields if
they use it.

### Association fields get no schemas

The Ecto adapter now builds the queries of the options of association fields:

- The query passed to the `:options_query` of `Backpex.Fields.HasMany` only has a named binding while the user searches
  the options, as your `:options_query` may name its own binding. Use a positional binding instead, e.g.
  `&where(&1, [user], user.role == :admin)`.
- `Backpex.Fields.HasManyThrough` still assigns the `:association`, but its `:pivot` and `:child` no longer have a
  `:queryable` key. Check your templates if they read the schemas from it.

### The form runs `before_changeset` on mount

The form of the `:new` and `:edit` actions builds its first changeset through `c:Backpex.Adapter.change/6`, as it does
on every change. So the `c:Backpex.Field.before_changeset/5` callbacks of the fields now also run on mount, and the
`create_changeset` or `update_changeset` function receives a changeset instead of the item. A function that passes its
first argument to `Ecto.Changeset.cast/4` works with both. If your changeset function or `before_changeset/5` callback
expects a struct, or has effects that should only happen on change, update it.

### Search casts columns that are not strings to text

Backpex compared every searchable column to the search string with `ilike`. Only `Backpex.Fields.Number` and
`Backpex.Fields.Currency` cast their column to text first. Now the Ecto adapter casts every column whose type in the
schema is not a string, whatever the field, e.g. the numeric `display_field` of a `Backpex.Fields.BelongsTo` field. It
also casts columns the schema doesn't know, e.g. a column of a join in the `item_query` under a `:custom_alias`. String
columns are compared as before.

### Deleting items

`Backpex.Resource.delete_all/4` returns `{:error, :foreign_key_violation}` instead of raising when other data still
references an item. If you call it in your own item actions, handle this result:

```elixir
case Backpex.Resource.delete_all(items, socket.assigns, socket.assigns.live_resource, authorize?: false) do
  {:ok, deleted_items} ->
    {:ok, put_flash(socket, :info, "Deleted #{length(deleted_items)} items.")}

  {:error, :foreign_key_violation} ->
    {:ok, put_flash(socket, :error, "The items are still in use.")}
end
```

### Changed functions

- `search_options/3` of `Backpex.LiveResource` is now `Backpex.LiveResource.search_options/2`. It no longer takes the
  schema.
- `apply_criteria/3` of `Backpex.Adapters.Ecto` is now `Backpex.Adapters.Ecto.apply_criteria/4`. It takes the schema as
  the last argument.
- The `query` functions of `Backpex.Filters.Boolean`, `Backpex.Filters.Select`, `Backpex.Filters.MultiSelect` and
  `Backpex.Filters.Range` are now `condition` functions that return the condition of the filter, e.g.
  `Backpex.Filters.Range.condition/4`. `maybe_query/2` of `Backpex.Filters.Boolean` and `do_query/3` of
  `Backpex.Filters.Range` are gone, and so is `query/3` of `Backpex.Metrics.Value`.
