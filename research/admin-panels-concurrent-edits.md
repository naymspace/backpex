# How other admin panels handle concurrent edits and presence

Research for [#2573](https://github.com/naymspace/backpex/issues/2573), part of the map [#2571](https://github.com/naymspace/backpex/issues/2571) (concurrent editing of an item).

**Question:** How do other admin panels and CMSs handle two people editing the same record: detection, what the second saver sees, live notices while editing, and presence?

Sources were read on 2026-11-25 (repository state at the commits linked below). Where a tool has no such feature, the section says so and names what was searched. "Not found" means no primary source turned up, not that the absence is proven.

## Summary

| Tool | Detection on save | Default? | Conflict UI | Live notice in open form | Presence |
| --- | --- | --- | --- | --- | --- |
| **Filament** (core) | None | – | Last save wins | None | None |
| Filament + `kenepa/resource-lock` | Pessimistic lock row | Opt-in per model + page | Modal "locked", *Return* / *Unlock page* | – | Lock holder's name in the modal |
| Filament + `packstub/filament-coedit` | Three-way compare against the re-read record | Opt-in per page (trait) | Merge per field; dialog only for fields both changed (*Keep mine* / *Use theirs*) | "*Name* saved this record" + *Get their changes* | Avatars in header, name tag on focused field, table column |
| **Django Admin** (core) | None | – | Last save wins | None | None |
| Django + `django-concurrency` | Version field, checked in `UPDATE … WHERE` | Opt-in per model | Non-field form error "Record Modified"; changelist and actions get their own handling | None | None |
| **Rails** `lock_version` | Version column | On when the column exists | `ActiveRecord::StaleObjectError` (developer handles it) | – | – |
| Avo | No own handling | – | Any exception other than `RecordInvalid` becomes a base error on the form | None | None |
| ActiveAdmin | No own handling | – | `StaleObjectError` ends as a 500; maintainers call it out of scope | None | None |
| **Directus** | No check on item save; content hash on version promote | Collaborative editing opt-in (setting + WebSockets) | No conflict: everyone edits one shared, live-synced draft; field focus locks the field for others | Others' keystrokes appear live; "Item updated" toast after another save; deleted item navigates away | Avatar stack in header, avatar next to the field being edited |
| **Strapi** (core) | None | – | Last save wins | None | None |
| Strapi + `@notum-cz/strapi-plugin-record-locking` | Pessimistic lock over WebSocket | Opt-in plugin | Notice that someone edits; optional takeover | – | Who holds the lock |
| **Payload** | Pessimistic lock (default) + `updatedAt` comparison on the first form-state request | Locking on by default; stale check always on for updates without autosave | Lock modal: *Go back* / *View read-only* / *Take over*; stale modal: only *Reload document* | Stale modal (fires on the first change, not live); takeover modal for the displaced editor | Lock holder's e-mail in the lock modal, lock icon with tooltip in list rows and document header |

## Filament

**Core: no detection, no presence.** Filament's `EditRecord` page (branches 4.x, 5.x and 6.x) contains no version, `updated_at` or lock check ([EditRecord.php on 4.x](https://github.com/filamentphp/filament/blob/f4d4e5eb0c5065b6fcd481d948f0323bc06e243a/packages/panels/src/Resources/Pages/EditRecord.php)); the only `Locked` there is Livewire's attribute against tampering with public properties. Searching the Filament repository for `lock_version` / `optimistic` and its issues for concurrent-edit overwrites found nothing. The README of filament-coedit states it plainly: "In Filament, the last save wins" ([filament-coedit README](https://github.com/packstub/filament-coedit/blob/687e4695b10fd47dc3784843b887fa8bd3abb7cd/README.md)).

**Plugin `kenepa/resource-lock` (pessimistic).** Locks the record when a user opens `EditRecord` or a simple-resource edit modal; unlocks after a timeout, or on save or discard. Opt-in: a `HasLocks` trait on the model and `UsesResourceLock` on the page. Optional polling heartbeat ("SPA mode"), a lock manager resource and an *Unlock* button behind a gate. "Optimistic Locking" is listed under "Coming soon" ([README](https://github.com/kenepa/resource-lock/blob/0ee142c93c105f171923ccef3ac5a7bcdaa908f1/README.md)). The second user sees a modal: "*name* is currently editing this page, so it is currently locked for editing" with *Unlock page* and *Return* ([modal.php](https://github.com/kenepa/resource-lock/blob/0ee142c93c105f171923ccef3ac5a7bcdaa908f1/resources/lang/en/modal.php)). Identity: a `GetResourceLockOwnerAction` returns `$user->name` by default and can be replaced ([GetResourceLockOwnerAction.php](https://github.com/kenepa/resource-lock/blob/0ee142c93c105f171923ccef3ac5a7bcdaa908f1/src/Actions/GetResourceLockOwnerAction.php)).

**Plugin `packstub/filament-coedit` (optimistic, merge).** Published 2026-11-25 as v1.0.0 ([Packagist](https://packagist.org/packages/packstub/filament-coedit)), so new and unproven, but the closest match to the map's destination. From its [README](https://github.com/packstub/filament-coedit/blob/687e4695b10fd47dc3784843b887fa8bd3abb7cd/README.md):

- *Detection:* on save it reads the record again, fills it through the form and compares three versions per field: the form as opened, the form as saved, the record now. Fields only the other person changed keep their value, fields only you changed take yours, a field both changed the same way saves silently, a field both changed differently opens a dialog. Saves of the same record are serialized with a cache lock. Only fields on the form take part; timestamps and other non-form columns are never written or reported. A field can be left out of the merge (`getCoEditIgnoredFields/0`), and it then saves last-write-wins.
- *Conflict UI:* a dialog per contested field, *Keep mine* or *Use Ana's*. In modals (relation managers, simple resources, table edit actions) it works in two steps: the first submit stops and shows their values, a second submit decides.
- *Live notice:* "Ana saved this record" names who saved and what changed, with a *Get their changes* button that pulls their values into the open form.
- *Presence:* avatars of everyone else on the record, a name tag on the field each one is in, and a `PresenceColumn` for tables. Presence is a Livewire heartbeat into the cache (default every 4 s, drop-off after 20 s, idle stop after 600 s); no WebSockets, no migrations. Identity comes from the panel's `getFilamentName()` and `getFilamentAvatarUrl()`.
- *Opt-in:* a trait on the edit page, `HasPresence` on view pages, `->coEdit()` on modal edit actions.
- *Events:* `ChangesMerged`, `ConflictDetected`, `ConflictResolved` for audit logs.

## Django Admin

**Core: no detection, no presence.** No primary source documents a concurrent-edit check in `django.contrib.admin`. Ticket [#11313](https://code.djangoproject.com/ticket/11313) ("list_editable fields don't support 'save' in multiuser environment") was closed in 2016 with a fix that makes `list_editable` "more resilient to concurrent edits" by matching POSTed rows by id; it adds no conflict detection, and the discussion points to django-concurrency.

**Package `django-concurrency` (optimistic).** ([README](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/README.md), [docs](https://django-concurrency.readthedocs.io/en/latest/))

- *Detection:* a version field on the model (`IntegerVersionField`, `AutoIncVersionField`, `TriggerVersionField` that also catches writes from outside Django via a DB trigger, `ConditionalVersionField` that bumps only for chosen fields) ([fields](https://django-concurrency.readthedocs.io/en/latest/fields.html)). A stale save raises `RecordModifiedError`. Opt-in per model; can be disabled per block (`disable_concurrency`).
- *Change form:* `ConcurrentModelAdmin` uses `ConcurrentForm`, which carries the version in a hidden field and adds the non-field error "Record Modified" in `clean()` ([forms.py](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/src/concurrency/forms.py)). No diff, no force-overwrite. Outside the admin a 409 handler renders `409.html` with the submitted and the saved object in the context ([views.py](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/src/concurrency/views.py)).
- *Changelist `list_editable`:* the version per row is posted as `form-_concurrency_version_<pk>`. Policy `SILENT` (default) saves the other rows and reports "Records `…` have been modified and were not updated"; `ABORT_ALL` rolls back the whole formset ([admin.py](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/src/concurrency/admin.py), [config.py](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/src/concurrency/config.py)).
- *Admin actions (including delete):* the selected checkboxes carry `pk,version`; if any selected row changed, the action aborts with "One or more record were updated. (Probably by other user) The execution was aborted." With *select across all*, the check is skipped with a warning ([admin.py](https://github.com/saxix/django-concurrency/blob/78c29416b4094cc665282c58be5349847ffd867e/src/concurrency/admin.py)).
- *Live notice, presence:* none.

## Rails `lock_version`, Avo, ActiveAdmin

**Rails** ([ActiveRecord::Locking::Optimistic](https://api.rubyonrails.org/classes/ActiveRecord/Locking/Optimistic.html)): optimistic locking is on for any model whose table has a `lock_version` column (rename via `locking_column`, switch off via `lock_optimistically = false`). Each update increments it; a stale update or destroy raises `ActiveRecord::StaleObjectError`, and the developer is responsible for rescuing it and resolving the conflict. Across web requests the docs say to put `lock_version` into the form as a hidden field.

**Avo: no own handling.** Searching the Avo repository's code and issues for `lock_version`, `StaleObjectError` and "optimistic locking" found nothing. Avo's `update` saves through `perform_action_and_record_errors`, which rescues any exception other than `RecordInvalid` into a base error on the record and re-renders the form with "You missed something" ([base_controller.rb](https://github.com/avo-hq/avo/blob/f0d74d45ad2f3abd5469f5221ba0cb3ab50ea7ab/app/controllers/avo/base_controller.rb)). So a `StaleObjectError` would show up as a generic base error, but only if the submitted `lock_version` reaches the record, which Avo does not arrange by itself. No presence or live notice found.

**ActiveAdmin: out of scope.** Issue [#4422](https://github.com/activeadmin/activeadmin/issues/4422) "Optimistic Locking Not Supported" reports a 500 on `StaleObjectError`; a maintainer closed it in 2016: "I think Optimistic Locking is not in the scope of ActiveAdmin", pointing to inherited_resources and a gist as workaround. No presence or live notice found.

## Directus

**No check on a normal item save.** No version or hash check was found on item updates. Content versions are the exception: promoting a version requires a `mainHash` of the main item and fails with `VersionHashMismatchError` if the main item changed since ([versions.ts](https://github.com/directus/directus/blob/4856582eec1ea426f115b79a875c44c819fe0b9d/api/src/services/versions.ts)); the app then offers a comparison view to pick fields. Open issue [#28374](https://github.com/directus/directus/issues/28374) reports that auto-saves of the same version from two sessions silently overwrite each other, because "there's no conflict check on version saves".

**Collaborative editing (since 11.15, built in).** ([overview](https://directus.com/docs/guides/content/collaborative-editing), [usage](https://directus.com/docs/guides/content/collaborative-editing/usage), [configuration](https://directus.com/docs/guides/content/collaborative-editing/configuration))

- *Opt-in:* requires `WEBSOCKETS_ENABLED` (default `false`) and the project setting `collaborative_editing_enabled` (default `false`) ([env defaults](https://github.com/directus/directus/blob/4856582eec1ea426f115b79a875c44c819fe0b9d/packages/env/src/constants/defaults.ts), [migration](https://github.com/directus/directus/blob/4856582eec1ea426f115b79a875c44c819fe0b9d/api/src/database/migrations/20260128A-add-collaborative-editing.ts)). Several instances need a shared Redis.
- *Model:* there is no conflict to detect, because everyone in the item's "room" edits one shared draft. Each field change is broadcast and applied to the others' unsaved edits; a discard is broadcast too. When anyone saves, the others re-read the item, drop edits now equal to the saved values and get an "Item updated" toast; a deletion shows a persistent notice and navigates away ([use-collab.ts](https://github.com/directus/directus/blob/4856582eec1ea426f115b79a875c44c819fe0b9d/app/src/composables/use-collab.ts)).
- *Field locking:* "Field locking prevents you from editing fields others are actively using", released when they move away. Translations lock as a whole; a relational drawer locks the whole M2A/M2M interface.
- *Presence:* an avatar stack in the item header (hover shows the name, click scrolls to the focused field) and avatars next to the field someone is editing. Identity is the Directus user: `first_name`, `last_name` and `avatar`, plus a colour per session ([CollabIndicatorHeader.vue](https://github.com/directus/directus/blob/4856582eec1ea426f115b79a875c44c819fe0b9d/app/src/views/private/components/collab/CollabIndicatorHeader.vue)). Collaboration respects existing permissions.

## Strapi

**Core: no detection, no presence.** The Content Manager's update controller loads the draft, checks permissions and writes the sanitized body, without comparing any version or `updatedAt` ([collection-types.ts](https://github.com/strapi/strapi/blob/2da4ca236ade35565cbf824bbe981610b21964ab/packages/core/content-manager/server/src/controllers/collection-types.ts)). The only "lock" in the edit view is the i18n shared-fields lock, unrelated to other users ([EditViewPage.tsx](https://github.com/strapi/strapi/blob/2da4ca236ade35565cbf824bbe981610b21964ab/packages/core/content-manager/admin/src/pages/EditView/EditViewPage.tsx)). A feature request for locking or an "A is editing" alert ([#5223](https://github.com/strapi/strapi/issues/5223)) was closed for not following the template and redirected to Strapi's Product Board.

**Plugin `@notum-cz/strapi-plugin-record-locking` (pessimistic).** Notifies users that someone else edits the record and prevents concurrent edits; optional takeover button (`showTakeoverButton`, default `false`) that notifies the displaced user; `include`/`exclude` per content type, all types locked by default once installed; Socket.IO transports ([README](https://github.com/notum-cz/strapi-plugin-record-locking/blob/6528fbd2203c3bb6bd275e427f7d3b97d8fe95f6/README.md)). The README does not say how the user's identity is displayed.

## Payload

**Document locking (pessimistic), on by default.** ([docs](https://payloadcms.com/docs/admin/locked-documents))

- *Config:* `lockDocuments` on each collection and global; `false` disables it, `{ duration }` sets the inactivity timeout in seconds (default 300). The lock is taken when a user starts editing and released when they leave the edit view or after the timeout. The edit view refreshes it on form-state requests at most every 10 s ([useFormState.ts](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/forms/Form/useFormState.ts)).
- *Second user:* a modal "Document locked": "*email* is currently editing this document. If you take over, they will be blocked from continuing to edit, and may also lose unsaved changes", plus "Edited since *time*", with *Go back*, *View read-only* and *Take over* ([DocumentLocked](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/elements/DocumentLocked/index.tsx)).
- *Displaced user:* after a takeover, a modal "Editing taken over" with *View read-only* and *Back to dashboard* ([DocumentTakeOver](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/elements/DocumentTakeOver/index.tsx)). The client learns about the new lock holder from the lock state returned with form-state responses, so this appears on the next form-state request, not by push ([useFormState.ts](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/forms/Form/useFormState.ts)).
- *Presence:* only the lock holder. Shown as e-mail (falling back to the id) in the modal, and as a lock icon with "*email* is editing" tooltip in list rows (in place of the select checkbox), the document header and dashboard cards ([Locked](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/elements/Locked/index.tsx)). Identity is not configurable in these components.
- *API:* the Local API's `update` and `delete` accept `overrideLock` (default `true`, i.e. ignore locks); with `false` they fail on a document locked by someone else ([docs](https://payloadcms.com/docs/admin/locked-documents)).

**Stale-data check (optimistic, on the first change).** On the first form-state request after loading or saving (in practice: the first change), the client sends the `updatedAt` it loaded; the server re-reads `updatedAt` and flags the document stale if it differs ([handleStaleDataCheck.ts](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/utilities/handleStaleDataCheck.ts), [buildFormState.ts](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/utilities/buildFormState.ts)). The check runs once per session, only for updates, and not for collections with autosave ([useFormState.ts](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/forms/Form/useFormState.ts)). The UI is a modal "Document modified": "This document was recently updated by another user. Your view is out of date." with a single *Reload document* button: no diff, no keep-mine ([DocumentStaleData](https://github.com/payloadcms/payload/blob/d90eddd98c2c3d6cb3ffb498a26b2f19257d1871/packages/ui/src/elements/DocumentStaleData/index.tsx)). No check was found in the save itself, so a change made after the first check can still be overwritten.

## Patterns worth considering for Backpex

1. **A version token travels with the form, the check sits in the write.** Rails (`lock_version` as hidden field), django-concurrency (hidden `VersionField`, `UPDATE … WHERE version = ?`) and Payload (`updatedAt` compared server-side) all compare what the form was loaded with against what is stored now. The Ecto counterpart is [`Ecto.Changeset.optimistic_lock/3`](https://hexdocs.pm/ecto/Ecto.Changeset.html#optimistic_lock/3), Ash has [`Ash.Resource.Change.OptimisticLock`](https://hexdocs.pm/ash/Ash.Resource.Change.OptimisticLock.html). A LiveView keeps the loaded item in assigns, so Backpex needs no hidden field, but the check must happen in the adapter's write, not just in a pre-read (Payload's single pre-check leaves a window).
2. **Opt-in per resource vs. on by default.** Version columns are opt-in everywhere (Rails turns on by column presence). Payload's locks are the only default-on mechanism. A check that needs no column (comparing the loaded item, like filament-coedit or Payload's `updatedAt`) could be on by default.
3. **Conflict UI spectrum.** Error only (django-concurrency "Record Modified", Avo base error), reload only (Payload), merge per field with a dialog only for fields both changed (filament-coedit), shared draft so no conflict (Directus). The per-field three-way rule of filament-coedit (opened / submitted / current) keeps non-overlapping changes without asking, and only asks about real conflicts.
4. **`index_editable` and actions need their own rule.** django-concurrency treats the changelist separately (per-row version, `SILENT` vs `ABORT_ALL`) and checks admin actions against `pk,version` pairs, skipping the check for *select all*. Rails checks destroy as well.
5. **Live notice when someone else saves.** Directus (toast after a save, re-read, keep own unsaved edits) and filament-coedit ("*Name* saved this record" + *Get their changes*) push the notice while the form is open; Payload only shows it on the next change. Backpex's PubSub events would fit the push model, but only cover writes through Backpex.
6. **Presence.** Header avatar stack (Directus, filament-coedit), field-level markers (Directus, filament-coedit), a list column (filament-coedit, Payload's lock icon). Identity comes from the app's user (Directus users; Filament's `getFilamentName/getFilamentAvatarUrl`; kenepa's overridable owner action). Payload hard-codes e-mail, which is the least flexible. Presence transport ranges from WebSockets (Directus, Notum) to a polled heartbeat (filament-coedit, kenepa); Phoenix.Presence covers this natively.
7. **Locks are the common plugin answer, but out of scope here.** Payload's default and the Filament and Strapi plugins are pessimistic locks with timeouts and takeover; they need heartbeats, expiry and a takeover flow, which the map excludes.
